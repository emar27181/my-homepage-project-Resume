v1のデザイン規約(Tailwindのデフォルトスケール、shadcn由来のCSS変数)は変更していない。ここではv2 (`/v2`) だけで使う独自トークンを記録する。実体は `src/v2/styles/terminal.css` の `.pf-computer` 内のCSS変数1箇所のみ。

## タイポグラフィ

- フォントは全面的にmonospace(`ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`)。
- 本文14px、入力欄は16px固定(iOS Safariの自動拡大を防ぐため。§05参照)。
- ASCII artは幅560px未満で"EMAR"、560px以上で"EMAR27181"(ハンドル名)を表示(`boot.ts#asciiArtFor`)。2つとも `asciiFont.ts` の同じ5行ブロックフォントから生成しており、手描きのASCII artを2つ持って食い違わせない設計。

## ボタン/チップ(アトミックデザイン)

v2でピル形状の見た目を持つ部品(ヘッダーのナビゲーション・モード切替・プロフィールの外部リンク・制作物カードの技術タグ・`open`コマンドで開くプレビューパネルの技術タグ)は、すべて `src/v2/components/atoms/Chip.astro` という1つのアトムから生成する。以前はプレビューパネルの技術タグだけ別のCSSルール(`.pf-preview .pf-tech span`)で高さ・フォントサイズが独自定義されており、Collageモードの制作物カードでは技術タグがChipですらなく無地の箇条書き(`<ul><li>`)になっていた。「同じ役割の部品を2箇所目に書く前に共通化する」という規約に反していたため、Chipアトム1つに統合した。

- 高さは2段階のみ(`pf-chip--sm` = 24px / `pf-chip--md` = 44px)。現状v2で使っているのは`sm`(補助操作・密なヘッダー・情報バッジ向け)のみで、`md`は将来タッチ主体の主要操作を置く場合のために定義だけ用意してある。
- 同じ行・同じグループに並ぶ部品は必ず同じ`size`を指定する(ヘッダーのv1リンクとモード切替、プロフィールの外部リンク3つ、技術タグの並びなど)。
- 状態(アクティブ/非アクティブ)は`active`propで塗り(背景色)だけを変える。枠線の太さやサイズは変えない(規約04-4「状態で外形を変えない」)。
- `as="a"|"button"`のときだけ`cursor:pointer`とhoverが効く。`as="span"`(既定値、技術タグなど非対話的な用途)は同じ見た目のまま静的に表示される。
- モード切替(collage/terminal)は`src/v2/components/molecules/SegmentedControl.astro`というmolecule。Chipアトムをどう並べるかだけを知っていて、各選択肢の意味(ドメイン語)は持たない。
- クライアントサイドJS(`app.ts`)が`open`コマンドで動的に生成するプレビューパネルの技術タグも、同じ`pf-chip pf-chip--sm`クラスをJSから直接付与しており、Astroコンポーネントとして描画される他のChipと完全に同じ見た目になる(実測: 表示されているすべての`.pf-chip`要素の高さが24pxで一致することをPlaywrightで確認済み)。

ターミナル入力欄自体は44pxのタッチ領域を取っていない(キーボード操作前提のテキスト入力のため)。

### モバイルでのタッチ領域

高さの2段階(`--pf-touch-sm: 24px` / `--pf-touch-md: 44px`)は`.pf-computer`のCSS変数1箇所で定義し、`.pf-chip--sm`/`.pf-chip--md`と、幅560px以下向けのタッチ領域拡大の両方がここから値を取る(`src/v2/styles/terminal.css`)。

- 560px以下では、操作可能なチップ(`a.pf-chip`/`button.pf-chip`、つまりヘッダーのナビゲーション・モード切替・プロフィールの外部リンク・`open`ボタン)だけが`--pf-touch-md`(44px)に拡大される。
- 非対話的な`span.pf-chip`(技術タグなど)は拡大しない。タップ対象ではない情報バッジを44pxまで広げると、密度が落ちてかえって見づらくなるため。
- ブレークポイントはASCII artの幅切り替え(`boot.ts#asciiArtFor`)と同じ560pxを再利用しており、v2内で「狭い画面」の基準値を1つに揃えている。

### モバイルでターミナルウィンドウが小さく見えていた不具合

実機(iOS Safari)で、ターミナルウィンドウがアドレスバー表示中にかなり小さく見える不具合があった。原因は3つ重なっていた。

1. `vh`はブラウザの「アドレスバーが隠れた最大のビューポート」基準で計算されるため、アドレスバー表示中は実際に見えている領域より`vh`の値が大きく評価され、結果的に指定した高さの割合が小さく見えてしまう。→ 動的ビューポート単位`dvh`にフォールバック対応(`height: min(70vh, 640px); height: min(70dvh, 640px);` のように2行書き、`dvh`未対応ブラウザは1行目のまま)。
2. `.pf-terminal-layout`が`flex-direction: column`になるモバイル幅では、`.pf-window`の`flex-basis`(デスクトップでは幅60%の指定)が縦方向の主軸サイズとして再解釈され、かつ親コンテナの高さが未指定のため「中身に合わせたサイズ」にフォールバックし、明示した`height`を無視してしまっていた。→ モバイル幅では`flex: 1 1 auto`にして`flex-basis`を`auto`に戻し、`height`指定を効かせる。
3. Flexアイテムは既定で`min-height: auto`となり、指定した`height`より中身が大きい場合は中身に合わせて伸びてしまう(横方向のflexでは問題にならないが、縦方向で顕在化する)。→ `.pf-window`と`.pf-window__body`の両方に`min-height: 0`を指定し、内部を正しくスクロールさせる。

3つとも`src/v2/styles/terminal.css`に集約されており、実測(Playwrightでビューポート390×560を再現)でウィンドウ高さが`min(80dvh, 640px)`どおり448pxになり、中身507px分は内部スクロールで収まることを確認済み。

### v1ヘッダーとの整合(IconButton)

v1のヘッダーには元々、ダークモード切り替えボタンの独自スタイル(`rounded-md border border-border p-1.5`)と、v2ページへのリンクとして後から追加したテキストリンクが並んでいたが、パディングの取り方が違うため見た目のサイズが揃っていなかった。`src/components/IconButton.astro`という固定サイズ(`h-8 w-8` = 32×32px)のアトムを1つ作り、両方をそこから生成するように統一した(実測で両方とも32×32pxに一致することを確認済み)。同じ行に並ぶ操作は必ず同じ段階にする、という規約に沿っている。

## 角の丸み

- ウィンドウ・カード・プレビューパネル: 8px (`border-radius: 8px`、v1の`--radius: 0.5rem`と同じ値に合わせている)。
- チップ・信号ドット: 完全な円(`border-radius: 9999px`)。

## レスポンシブ

- 860px未満でターミナルとプレビューパネルを縦積みに切り替え(`.pf-terminal-layout`)。
- `body`に`overflow-x: hidden`を明示し、入力欄・ウィンドウ・プレビューパネルすべてに`min-width: 0`を指定。実測: 390px幅で`document.documentElement.scrollWidth === clientWidth`を確認済み(横スクロールが出ない)。

## 出典

- 44px/24pxの操作部品の2段階、16px固定の入力欄という一般則はCLAUDE運用ルールの持ち歩くフロントエンド規約(Apple HIG 44pt / WCAG 2.2 AA 2.5.8 / iOS Safariのズーム挙動)に準拠しており、v2でも同じ下限だけは踏襲している(ただしv2はキーボード入力中心のUIのため、タッチ領域44pxを機械的に全部品へ適用してはいない)。
